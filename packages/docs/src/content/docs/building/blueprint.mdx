Blueprints are TOML files that declaratively define your application. This page covers the core data, page, UI, authentication, and integration sections. Domain behavior has a dedicated [Domain Commands](/building/domain-commands) reference, while [Workflows](/building/workflows) and [Skills](/reference/skills) cover their respective sections in depth.

## Project

Every blueprint starts with a version and project metadata:

```toml
version = "0.6.0"

[project]
name = "My App"
version = "1.0.0"
description = "An internal tool"

[project.runtime]
min_version = "0.6.0"
```

## Composing multiple TOML files

Large applications can split a Blueprint into explicitly imported TOML fragments. Put `imports` at the top of the root file, before any table declaration:

```toml
imports = [
  "./foundation/design-system.toml",
  "./domain/requests/module.toml",
]

version = "0.6.0"

[project]
name = "My App"
version = "1.0.0"

[project.runtime]
min_version = "0.6.0"
```

Fragments can import other fragments. Each path is resolved relative to the file containing it, so a directory can own its composition without registering names globally:

```toml
# domain/requests/module.toml
imports = ["./entities.toml", "./commands.toml", "./workflows.toml"]
```

Only the root file defines `version` and `project`. Imported files can use any `.toml` filename and contain any other Blueprint sections. Runtime names remain application-global: two imported files cannot both define the same entity, command, workflow, page, service, skill, or plugin.

Imports must name explicit relative `.toml` files. Globs, absolute paths, files outside the root Blueprint directory, cycles, and ambiguous singleton configuration are rejected. Importing the same canonical file through multiple branches incorporates it once, which allows a shared `design-system.toml` to be reused safely.

## Entities

Entities define your data model. The runtime creates database tables automatically.

```toml
[entity.Post]
fields = [
  { name = "id", type = "ULID", primary_key = true },
  { name = "title", type = "Text", required = true },
  { name = "body", type = "LongText", required = true },
  { name = "status", type = "Enum", values = ["draft", "published"], default = "draft" },
  { name = "authorId", type = "Ref", ref = "User.id", index = true },
  { name = "createdAt", type = "DateTime", default = "now" }
]
```

### Field Types

| Type | Description |
|------|-------------|
| `ULID` | Primary key, auto-generated unique identifier |
| `UUID` | UUID identifier |
| `Text` | Short text (VARCHAR) |
| `LongText` | Long text (TEXT) |
| `Email` | Email address with validation |
| `Integer` | Whole numbers |
| `Float` | Decimal numbers |
| `Boolean` | true/false |
| `DateTime` | Date and time (shown with its time zone) |
| `Date` | Date only |
| `JSON` | JSON data |
| `Enum` | Enumerated values (use `values = [...]`) |
| `Ref` | Foreign key reference (use `ref = "Entity.field"`) |

### Field Options

| Option | Type | Description |
|--------|------|-------------|
| `primary_key` | boolean | Mark as primary key |
| `unique` | boolean | Enforce uniqueness |
| `index` | boolean | Create database index |
| `required` | boolean | Cannot be null |
| `nullable` | boolean | Explicitly allow null |
| `default` | any | Default value (`"now"` for DateTime) |
| `values` | string[] | Allowed values for Enum type |
| `ref` | string | Foreign key target for Ref type |
| `write` | `"command-only"` | Reject generic writes to a lifecycle field |
| `commands` | string[] | Commands allowed to write a command-only field |

### Indexes and Entity Protection

Define compound or named indexes with `[[entity.Post.indexes]]`:

```toml
[[entity.Post.indexes]]
fields = ["authorId", "status"]
name = "post_author_status"

[[entity.Post.indexes]]
fields = ["slug"]
unique = true
```

Protect several fields with one command allowlist:

```toml
[entity.Post.protection]
fields = ["status", "publishedAt"]
commands = ["PublishPost", "UnpublishPost"]
```

See [Domain Commands](/building/domain-commands#protect-lifecycle-fields) for command-only mutation behavior.

### Relations

```toml
[entity.User.relations]
posts = { type = "hasMany", entity = "Post", foreign_key = "authorId" }

[entity.Post.relations]
author = { type = "belongsTo", entity = "User", foreign_key = "authorId" }
```

Relation types: `hasMany`, `hasOne`, `belongsTo`, `manyToMany` (requires `through`).

### Access Control

Define who can read, create, update, or delete records:

```toml
# Simple boolean
[entity.Post.access]
read = true
create = true
update = { authorId = "$currentUser.id" }
delete = { "$currentUser.role" = "admin" }
```

Use `$currentUser` to reference the logged-in user's fields. Combine conditions with `or`/`and`:

```toml
[entity.Post.access]
read = { or = [{ status = "published" }, { authorId = "$currentUser.id" }] }
```

Field-level access:

```toml
[entity.User]
fields = [
  { name = "email", type = "Email", access = { read = true, write = { "$currentUser.role" = "admin" } } }
]
```

## Pages

Pages bind URL paths to layouts and queries.

Set `live = true` on a page to keep its server-rendered main content synchronized with committed mutations on Node and Workers. See [Live Mode](/building/live-mode) for browser behavior and limitations.

Pages can also mount interactive widgets directly under `[page."/path".widget]`. For the current widget types and examples, see [Widgets](/building/widgets), [Board Widget](/building/widgets/board), and [Lookup Widget](/building/widgets/lookup).

### Layout Types

| Layout | Description |
|--------|-------------|
| `list` | Table view of query results |
| `detail` | Single record display |
| `form` | Create/update/delete forms |
| `dashboard` | Widgets and summary cards |
| `auth` | Authentication pages (sign-in) |

### List Page

```toml
[page."/posts"]
title = "All Posts"
auth = "none"
layout = "list"

[page."/posts".query.posts]
entity = "Post"
where = { status = "published" }
orderBy = { createdAt = "desc" }
limit = 20
include = ["author"]
```

### Detail Page

```toml
[page."/posts/:id"]
title = "Post Detail"
auth = "none"
layout = "detail"

[page."/posts/:id".query.post]
entity = "Post"
where = { id = "$params.id" }
include = ["author"]
```

### How values are displayed

Detail pages and related lists show each field according to its type. All values are HTML-escaped. Line breaks in `LongText`
and `JSON` are kept on detail pages and in activity feeds; table cells show values on one line.

| Type | Display |
|------|---------|
| `LongText` | Line breaks are kept (detail pages) and long lines wrap |
| `JSON` | Pretty-printed (monospaced on detail pages). Keys that look like technical identifiers (for example `id`) are left out |
| `DateTime` | Date, time and time zone, such as `10/8/2026, 2:13:42 AM UTC` |
| `Date` | Date only |
| `Boolean` | A check or cross mark |
| empty | `-` |

The time zone is the **server's**: Cloudflare Workers always render in UTC, and the Node runtime uses the process's zone. The
zone is named so a reader in another zone is not misled.

Queries other than the page's main record appear as related sections below it. Zebric chooses how to present each one from
the entity's name, which is worth knowing when a section does not look the way you expect:

| Entity name contains | Presented as |
|----------------------|--------------|
| `task` | A checklist |
| `milestone` or `timeline` | A timeline |
| `activity` or `event` | An activity feed |
| anything else | A table |

An **activity feed** shows, for each record, the first of `title`, `summary`, `action`, `kind`, `type` or `name` as its heading;
the first of `detail`, `description` or `message` beneath it (line breaks kept); and the first of `timestamp` or `createdAt` as
its time. A record with none of these fields shows the word "Event".

### Dashboard Page

```toml
[page."/"]
title = "Dashboard"
auth = "required"
layout = "dashboard"

[page."/".query.recentPosts]
entity = "Post"
orderBy = { createdAt = "desc" }
limit = 5

[page."/".query.totalUsers]
entity = "User"
```

### Query Options

| Option | Description |
|--------|-------------|
| `entity` | Entity to query |
| `where` | Filter conditions (use `$params.id` for URL params) |
| `orderBy` | Sort order (`{ field = "asc" }` or `"desc"`) |
| `limit` | Maximum number of results |
| `offset` | Skip N results |
| `include` | Related entities to include |

## Widgets

Widgets are page-level interactive views that live alongside standard page configuration:

```toml
[page."/customers"]
title = "Customer Search"

[page."/customers".widget]
kind = "lookup"
entity = "Customer"
search = ["lastName", "firstName", "email"]
```

Use widgets when a page should behave more like a tool than a traditional CRUD screen. Zebric currently supports:

- `board` for Kanban-style issue and workflow pages
- `lookup` for standalone search-and-select pages

For full widget configuration and examples, see [Widgets](/building/widgets), [Board Widget](/building/widgets/board), and [Lookup Widget](/building/widgets/lookup).

## Forms

Forms handle record creation and updates.

```toml
[page."/posts/new"]
title = "New Post"
auth = "required"
layout = "form"

[page."/posts/new".form]
entity = "Post"
method = "create"

[[page."/posts/new".form.fields]]
name = "title"
type = "text"
label = "Title"
required = true

[[page."/posts/new".form.fields]]
name = "category"
type = "select"
label = "Category"
options = [
  { value = "general", label = "General" },
  { value = "finance", label = "Finance" }
]

[[page."/posts/new".form.fields]]
name = "body"
type = "textarea"
label = "Content"
rows = 10
required = true

[page."/posts/new".form.onSuccess]
redirect = "/posts/{id}"
message = "Post created!"
```

### Form Field Types

`text`, `textarea`, `email`, `password`, `number`, `select`, `checkbox`, `radio`, `file`, `date`, `datetime`, `hidden`

Use `hidden` for technical values that must be submitted with a form but should
not be presented to the user, such as a parent record identifier.

### Form Field Options

| Option | Description |
|--------|-------------|
| `label` | Display label |
| `placeholder` | Placeholder text |
| `required` | Field is required |
| `default` | Default value |
| `options` | Choices for select/radio (string array or `{ value, label }` objects) |
| `rows` | Number of rows for textarea |
| `pattern` | Regex validation pattern |
| `error_message` | Custom error message |
| `min` / `max` | Number range constraints |
| `accept` | Accepted file types for file input |

## Action Bar

Detail pages can include an action bar with workflow triggers and a status badge. They render domain commands for the primary entity when the command's policy and `availableWhen` checks pass, even when no explicit action-bar block is present:

```toml
[page."/issues/:id"]
title = "Issue Detail"
layout = "detail"

[page."/issues/:id".actionBar]
statusField = "status"

[[page."/issues/:id".actionBar.actions]]
label = "Set Status"
workflow = "SetIssueStatus"
style = "primary"

[[page."/issues/:id".actionBar.actions]]
label = "Request Approval"
workflow = "RequestApprovalIfNeeded"
style = "secondary"
visibleWhen = { status = ["draft", "changes_requested"] }
```

Command actions do not need to be repeated in `actionBar.actions`; define their label, input, confirmation prompt, and style on the command. See [Generated UI](/building/domain-commands#generated-ui).

Workflow and link actions support `visibleWhen` and `enabledWhen` record conditions, along with `confirm`, `payload`, `redirect`, `successMessage`, and `errorMessage`. Put authoritative state checks in the workflow or command as well; UI visibility is not an authorization boundary.

## Layout Slots

Customize layout rendering with named slots:

| Layout | Available Slots |
|--------|----------------|
| `list` | `list.header`, `list.body`, `list.empty` |
| `detail` | `detail.main`, `detail.related` |
| `form` | `form.form` |
| `dashboard` | `dashboard.widgets` |

## UI Configuration

```toml
[ui]
render_mode = "server"
theme = "default"
progressive_enhancement = "none"  # "none", "alpine", or "htmx"
view_transitions = true

[ui.tailwind]
primary_color = "#3B82F6"
```

### Theming

Zazzle selects visual styles through `[design_system]`. The default is `modern`;
`classic`, `friendly`, and `minimal` are also built in, each with a dark palette.

```toml
[design_system]
name = "acme"
extends = "friendly"
css = ["/styles/acme.css"]

[design_system.tokens]
color-primary = "#5636cc"
color-error = "#a12622"
color-info = "#24548a"
font-family-heading = "Georgia, serif"
```

Token names become `--zb-*` CSS custom properties. Generated details, related
feeds, action bars, status badges, feedback, and form controls use semantic
classes so their colors follow the selected system. Success uses `color-success`,
warning uses `color-warning`, and errors and destructive actions use `color-error`.
Informational feedback uses `color-info`. Status badges and feedback use
`surface-card` as their background.

The navigation color-mode control cycles auto/light/dark and saves the visitor's
choice locally. Custom token overrides apply to the light palette; inherited dark
colors come from the base system. Use CSS scoped to
`html[data-zebric-design-system="acme"][data-zebric-resolved-color-mode="dark"]`
to customize dark colors.

The renderer ships two `Theme` objects — `defaultTheme` (light) and `darkTheme` — exported from `@zebric/runtime-core`. The `theme` field above is accepted by the schema but not yet wired up to select between them automatically; applying a different theme currently requires passing a `Theme` object to the renderer programmatically rather than by name in the blueprint.

### Progressive Enhancement

Any value other than `"none"` enables client-side form enhancement: forms render with a `data-enhance` attribute, and a small inline script intercepts submits, does an AJAX `fetch` with CSRF-token forwarding, shows a loading state on the submit button, and redirects or displays inline field errors based on the JSON response — no full page reload. The `"alpine"` and `"htmx"` values are accepted by the schema but don't currently load those libraries; they behave the same as any non-`"none"` value.

### View Transitions

`view_transitions = true` adds a `<meta name="view-transition">` tag and `@view-transition` CSS so supporting browsers animate page navigations.

### Content Negotiation

Every page responds with HTML by default, or JSON if the request's `Accept` header includes `application/json` without also including `text/html`:

```bash
curl http://localhost:3000/posts                                   # HTML
curl -H "Accept: application/json" http://localhost:3000/posts     # JSON
```

### Accessibility

Rendered pages include WCAG-oriented features: a skip-to-content link, `aria-label`/`aria-current` on navigation, table `<caption>` and `scope="col"` headers, `aria-describedby`/`aria-invalid`/`role="alert"` on form validation errors, and an `sr-only` utility class for screen-reader-only content.

## Authentication

```toml
[auth]
providers = ["email"]
trustedOrigins = ["http://localhost:3000"]

[[auth.apiKeys]]
name = "my-agent"
keyEnv = "MY_API_KEY"
agentId = "content-agent"
credentialId = "content-agent-production"
displayName = "Content Agent"
roles = ["editor"]
scopes = ["entity.post.list", "posts.publish"]
```

API keys can authenticate entity, skill, workflow, command, job, and audit routes. See [Security & Authentication](/building/security#api-keys) for identity and scope behavior.

## Domain Commands

Commands define guarded business transitions shared by UI, HTTP, agents, and workflows:

```toml
[command.PublishPost]
entity = "Post"
label = "Publish"
policy = "actor.roles contains 'editor'"
availableWhen = "record.status == 'draft'"
mutations = { status = "published", publishedAt = "now" }
scopes = ["posts.publish"]
```

See [Domain Commands](/building/domain-commands) for typed input, protected fields, handlers, generated UI, workflow steps, and HTTP invocation.

## External Services

Services declare typed operations supplied by a loaded plugin:

```toml
[service.crm]
description = "Customer system"
plugin = "crm-plugin"

[service.crm.operations.lookupCustomer]
description = "Find a customer by email."

[service.crm.operations.lookupCustomer.input.email]
type = "Email"
required = true

[service.crm.operations.lookupCustomer.result]
type = "Object"
fields = { id = { type = "Text", required = true }, name = { type = "Text" } }
allowUnknown = false
```

Each service requires at least one operation. Input and result schemas accept entity scalar types plus nested `Object` and `Array` values. `Object` requires `fields`; `Array` requires `items`. The optional `transform` map projects a validated external result before returning it to the caller.

## Notifications

```toml
[notifications]
default = "console"

[[notifications.adapters]]
name = "console"
type = "console"

[[notifications.adapters]]
name = "slack_ops"
type = "slack"
[notifications.adapters.config]
botTokenEnv = "SLACK_BOT_TOKEN"
defaultChannel = "#ops"
```

Adapter types: `console`, `slack`, `email`.
